## Top Findings

1. **High — HTTP error logs persist unfiltered request payloads.** `server/src/middleware/logger.ts:29–44,53–85` writes to `server.log`, includes raw request URLs in messages, and adds bodies, parameters and queries on responses with status >=400. `server/src/middleware/error-handler.ts:20–27` also attaches raw request fields for later logging. No Pino redaction configuration is present in this logger. `server/src/app.ts:81–88` mounts it after JSON parsing, so parsed bodies are available. This can copy private prompts, personal data or sensitive request fields into persistent logs, including on rejected requests. `server/src/log-redaction.ts` and its tests only address usernames/home paths and are not wired into this logger. Prefer an allowlist of diagnostic metadata, bounded sanitized errors, and tests of the actual HTTP logging boundary. This is source evidence of a privacy risk, not a claim that a live disclosure occurred; no logs or credentials were inspected.

2. **Medium — Local storage reports filesystem failures as absence or successful deletion.** `server/src/storage/local-disk-provider.ts:30–35,54–71,80–86` catches every `stat`/`unlink` error. Permission errors and I/O failures therefore become 404/`exists:false`, or a resolved delete even when bytes remain. This masks infrastructure faults and makes retention/deletion outcomes unreliable. `server/src/__tests__/storage-local-provider.test.ts:24–77` covers round trips, cross-company rejection and repeated deletion, but not permission/I/O failures. Suppress only expected missing-file errors; propagate unexpected failures.

3. **Medium — Dependency-changing PRs can be blocked by incompatible lockfile rules.** `.github/workflows/pr.yml:23–29` rejects lockfile edits outside the refresh branch. Its policy job regenerates a lockfile when manifests change (`83–89`), but that result is neither committed nor transferred to the independently checked-out verify/e2e jobs, which use frozen installs (`97–112,135–150`). `.github/workflows/refresh-lockfile.yml:3–7,37–38,74–79` ordinarily refreshes only after a master push. A PR that changes dependency requirements enough to invalidate the tracked lockfile can thus pass policy resolution but fail verification before the post-merge repair is available. Allow reviewed manifest/lockfile pairs or explicitly transfer a deterministic lockfile into verification. This is static workflow analysis, not a reproduced CI run.
